# DEBRI-Toolkit — полная техническая документация

Данный документ описывает работу набора скриптов **DEBRI-Toolkit**, предназначенного для первичной проверки хоста на признаки компрометации.

Основной короткий файл: [`README.md`](README.md).

Расшифровка названия:

```text
DEBRI — Debian/Ubuntu Bash Response & Inspection
```

---

## 1. Назначение проекта

**DEBRI-Toolkit** предназначен для:

- первичного триажа возможной компрометации;
- сбора диагностических артефактов;
- поиска очевидных красных флагов;
- проверки целостности пакетов;
- анализа модулей ядра, автозапуска, сети, пользователей, SSH, UEFI/GRUB;
- поиска расширенных аномалий процессов и памяти;
- формирования краткой сводки подозрительных находок;
- упаковки результатов для передачи аналитику;
- последующей очистки установленных диагностических пакетов и логов.

Набор **не является**:

- полноценным антивирусом;
- гарантированным средством обнаружения руткитов;
- заменой офлайн-форензики;
- заменой анализа оперативной памяти;
- заменой EDR/XDR;
- средством автоматического лечения системы.

---

## 2. Важное предупреждение

> [!WARNING]
> Проверка изнутри работающей системы не даёт 100% гарантии, если ядро, загрузчик или привилегированные процессы уже скомпрометированы.
>
> Руткит может скрывать:
>
> - процессы;
> - файлы;
> - модули ядра;
> - сетевые соединения;
> - записи в логах;
> - изменения конфигурации.

Если есть серьёзные подозрения:

1. Сначала сохраните собранные логи.
2. Не вводите важные пароли и ключи на подозрительной системе.
3. По возможности выполните проверку с чистого Live USB.
4. При подтверждении компрометации переустановите систему и замените все секреты.

## 5. Размещение и установка

### Вариант 1. Клонирование репозитория

```bash
git clone https://github.com/<owner>/<repo>.git
cd <repo>
chmod +x *.sh
sudo ./ir_check.sh
```

### Вариант 2. Ручное копирование

```bash
mkdir -p ~/ir-toolkit
cp /path/to/scripts/*.sh ~/ir-toolkit/
cd ~/ir-toolkit
chmod +x *.sh
```

Альтернативный вариант через `install`:

```bash
mkdir -p ~/ir-toolkit
install -m 0755 /path/to/scripts/*.sh ~/ir-toolkit/
```

## 7. Прогресс выполнения

Во время выполнения проверок через `ir_check.sh` может выводиться статус в процентах.

Пример:

```text
[  0%] [0/7] Начинаем проверку. Всего шагов: 7
[ 14%] [1/7] Запуск: 10_ir_basic.sh
[ 14%] [1/7] Завершено: 10_ir_basic.sh
[ 28%] [2/7] Запуск: 15_ir_anomalies.sh
[ 28%] [2/7] Завершено: 15_ir_anomalies.sh
...
[100%] [7/7] Все проверки завершены
```

Особенности:

- прогресс считается по количеству проверочных скриптов;
- внутренние команды отдельного скрипта не имеют отдельного процента;
- статус дублируется в:

```text
/root/ir/latest/progress.log
```

Просмотр прогресса из другого терминала:

```bash
tail -f /root/ir/latest/progress.log
```

## 8. Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `IR_DIR` | Каталог для логов и состояния. | `/root/ir` |
| `SSH_AUDIT_USER` | Пользователь для проверки `sshd -T -C`. | `root` |
| `SSH_AUDIT_HOST` | Хост для проверки `sshd -T -C`. | `localhost` |
| `SSH_AUDIT_ADDR` | Адрес клиента для проверки `sshd -T -C`. | `127.0.0.1` |
| `IR_ENABLE_LSOF_PROC` | Включает медленный `lsof +D /proc` в `15_ir_anomalies.sh`. | `0` |

Пример с другим каталогом логов:

```bash
sudo env IR_DIR=/var/ir ./ir_check.sh full
```

Пример проверки SSH для конкретного подключения:

```bash
sudo env SSH_AUDIT_USER=admin SSH_AUDIT_HOST=server SSH_AUDIT_ADDR=192.0.2.10 \
  ./ir_check.sh ssh
```

Пример включения медленного `lsof +D /proc`:

```bash
sudo env IR_ENABLE_LSOF_PROC=1 ./ir_check.sh anomalies
```

> [!NOTE]
> При использовании `sudo` переменные окружения желательно передавать через `sudo env`, потому что `sudo` может очищать окружение.

## 9. Контроллер `ir_check.sh`

`ir_check.sh` — основная точка входа.

Он:

- создаёт каталог проверки;
- запускает отдельные скрипты;
- сохраняет ссылку `/root/ir/latest`;
- пишет прогресс выполнения;
- упаковывает отчёт;
- запускает очистку;
- предоставляет интерактивное меню.

### Запуск без параметров

```bash
sudo ./ir_check.sh
```

Откроется интерактивное меню.

### Основные команды

| Команда | Назначение |
|---|---|
| `menu` | Интерактивное меню. Используется по умолчанию. |
| `setup` | Установить базовые диагностические пакеты. |

| `basic` | Базовая проверка. |
| `anomalies` | Расширенные аномалии процессов, памяти, `netns`, `/proc/net/tcp`. |
| `ssh` | Аудит SSH, если `sshd` установлен. |
| `integrity` | Проверка целостности пакетов и подозрительных файлов. |
| `modules` | Проверка модулей ядра. |
| `boot` | Проверка boot/UEFI/GRUB. |
| `network` | Проверка сети, маршрутов, firewall, DNS. |
| `scanners` | Запуск `rkhunter`, `chkrootkit`, `lynis`, если установлены. |

## 10. Подробное описание скриптов

Назначения:

### 10.3. `15_ir_anomalies.sh`

Проверяет расширенные аномалии.

#### Что проверяется

1. Исполняемые регионы памяти с флагами `rwxp`:
   - анонимные;
   - связанные с `memfd`;
   - связанные с `(deleted)`.

2. Процессы с удалённым исполняемым файлом:

   ```text
   /proc/PID/exe -> ... (deleted)
   ```

3. Процессы, исполняющие `memfd`.

4. Сетевые namespace:
   - список процессов по `netns`;
   - количество уникальных `netns`;
   - именованные `netns`;
   - состояние контейнерных сервисов.

5. Открытые файловые дескрипторы к чужим `/proc/PID`.

6. Сравнение локальных IPv4 TCP-эндпоинтов из:

   ```text
   /proc/net/tcp
   ```

   и вывода:

   ```bash
   ss -tan
   ```

#### Создаваемые файлы

```text
15-anomalies.log
netns_snapshot.txt
proc_tcp_local.txt
ss_tcp_local.txt
```

#### Важные ограничения

- `rwxp` не всегда означает вредоносность;
- JIT-движки браузеров, Java, .NET, NodeJS могут создавать исполняемые регионы;
- удалённый `exe` может быть после обновления пакета;
- сетевые namespace могут быть у Docker, Podman, LXC, libvirt, VPN, браузерных песочниц;
- сравнение `/proc/net/tcp` и `ss` может давать ложные срабатывания из-за быстрых изменений состояния;
- простая проверка ориентирована на IPv4.

### 10.4. `16_ir_ssh_audit.sh`

Проверяет SSH, если установлен `sshd`.

Если `sshd` не установлен, скрипт сообщит об этом и пропустит SSH-проверки.

#### Что проверяется

- наличие пакета `openssh-server`;
- бинарник `sshd`;
- статус сервисов:
  - `ssh.service`
  - `sshd.service`
- проверка конфигурации:

  ```bash
  sshd -t
  ```

- эффективная конфигурация:

  ```bash
  sshd -T
  ```

- контекстная конфигурация:

  ```bash
  sshd -T -C user=...,host=...,addr=...
  ```

- важные параметры:
  - `Port`
  - `ListenAddress`
  - `AuthorizedKeysFile`
  - `AuthorizedKeysCommand`
  - `AuthorizedKeysCommandUser`
  - `TrustedUserCAKeys`
  - `AuthorizedPrincipalsFile`
  - `AuthorizedPrincipalsCommand`
  - `PermitRootLogin`
  - `PasswordAuthentication`
  - `PubkeyAuthentication`
  - `PermitEmptyPasswords`
  - `HostKey`
  - `HostCertificate`
  - `Include`
  - `Match`
  - `ForceCommand`

#### Создаваемые файлы

```text
16-ssh-audit.log
sshd-T.txt
sshd-T.err
sshd-T-context-*.txt
```

#### Проверка конкретного `Match`-контекста

По умолчанию:

```text
user=root
host=localhost
addr=127.0.0.1
```

Проверить другой контекст:

```bash
sudo env SSH_AUDIT_USER=admin SSH_AUDIT_HOST=server SSH_AUDIT_ADDR=203.0.113.10 \
  ./ir_check.sh ssh
```

Это важно, потому что `Match`-блоки могут менять поведение SSH для отдельных пользователей, хостов или адресов.

### 10.5. `20_ir_integrity.sh`

Проверяет целостность и подозрительные артефакты.

#### Что проверяется

- `dpkg -V`;
- `debsums`, если установлен;
- источники пакетов;
- настройки `apt`;
- исполняемые файлы в:
  - `/tmp`
  - `/var/tmp`
  - `/dev/shm`
- `setuid`/`setgid` файлы;
- capabilities;
- `/etc/ld.so.preload`;
- упоминания:
  - `LD_PRELOAD`
  - `LD_AUDIT`
- cron;
- подозрительные шаблоны в:
  - cron;
  - systemd;
  - shell startup files;
- история установки пакетов;
- ошибки в `journalctl`;
- логи SSH;
- целостность журнала через:

  ```bash
  journalctl --verify
  ```

Основной лог:

```text
20-integrity.log
```

---

### 10.6. `30_ir_modules.sh`

Проверяет модули ядра.

#### Что проверяется

- версия ядра;
- `kernel taint`;
- `sig_enforce`;
- `lockdown`;
- `kernel.modprobe`;
- загруженные модули;
- путь к файлу модуля;
- подпись модуля;
- владелец файла по `dpkg -S`;
- целостность пакетов ядра;
- ошибки подписи в `dmesg`;
- файлы модулей вне `/lib/modules`;
- DKMS;
- автозагрузка модулей;
- недавно изменённые файлы модулей.

Основной лог:

```text
30-modules.log
```

#### Признаки проблемы

- модуль загружен, но файл отсутствует;
- файл модуля находится в `/tmp`, `/dev/shm`, `/home`;
- `dpkg -S` не показывает владельца файла;
- файл модуля изменён после обновления без объяснения;
- есть ошибки подписи модулей;
- модуль не принадлежит известному пакету и не является осознанно установленным драйвером.

### 10.7. `40_ir_boot.sh`

Проверяет загрузчик и firmware.

#### Что проверяется

- тип firmware:
  - BIOS;
  - UEFI;
- записи `efibootmgr`;
- состояние Secure Boot;
- MOK-ключи;
- командная строка ядра;
- содержимое `/boot`;
- файлы в EFI System Partition;
- записи `/etc/fstab`, связанные с `/boot` и EFI;
- подозрительные строки в `grub.cfg`;
- пользовательские настройки GRUB;
- информация о BIOS/UEFI через `dmidecode`;
- firmware security через `fwupdmgr`, если доступен.

Основной лог:

```text
40-boot.log
```

#### Признаки проблемы

- неизвестные `.efi` файлы;
- неизвестные загрузочные записи;
- неожиданные параметры в `/proc/cmdline`;
- изменённые файлы в `/boot`;
- Secure Boot выключен без ведома администратора;
- неизвестные MOK-ключи;
- подозрительные записи в:
  - `/etc/default/grub`
  - `/etc/grub.d/40_custom`

- DNS;

### 10.12. `90_ir_cleanup.sh`

Скрипт очистки.

Может удалять:

- диагностические пакеты;
- правила аудита;
- логи и состояние в `/root/ir`.

> [!CAUTION]
> Очистка уничтожает собранные артефакты.
>
> Перед очисткой упакуйте отчёт:
>
> ```bash
> sudo ./ir_check.sh pack
> ```

#### Основные опции

| Опция | Назначение |
|---|---|
| `--packages` | Удалить пакеты, установленные скриптом проверки. |
| `--audit` | Удалить правила аудита, добавленные `80_ir_audit_ssh_rules.sh`. |
| `--logs` | Удалить каталог `/root/ir`. |
| `--all` | Выполнить всё перечисленное. |
| `--known-packages` | Использовать встроенный список пакетов, если нет файла состояния. |
| `--autoremove` | Выполнить `apt-get autoremove --purge` после удаления пакетов. |
| `--dry-run` | Только показать действия, ничего не выполнять. |
| `--force` | Не спрашивать подтверждения. |

#### Примеры

Посмотреть, что будет сделано:

```bash
sudo ./90_ir_cleanup.sh --dry-run --all
```

Удалить пакеты:

```bash
sudo ./90_ir_cleanup.sh --packages
```

Удалить правила аудита:

```bash
sudo ./90_ir_cleanup.sh --audit
```

Удалить логи:

```bash
sudo ./90_ir_cleanup.sh --logs
```

Удалить всё:

```bash
sudo ./90_ir_cleanup.sh --all
```

Удалить всё, включая известный список пакетов без файла состояния:

```bash
sudo ./90_ir_cleanup.sh --all --known-packages
```

Удалить всё без подтверждений:

```bash
sudo ./90_ir_cleanup.sh --all --known-packages --autoremove --force
```

> [!WARNING]
> Встроенный список `--known-packages` намеренно не включает потенциально критичные пакеты, такие как `ca-certificates`.
>
> Для удаления таких пакетов используется файл состояния, если они были установлены скриптом.

## 13. Красные флаги

### Высокая подозрительность

- неизвестный процесс с внешним сетевым соединением;
- процесс с удалённым `exe` и сетевой активностью;
- исполняемый файл в `/tmp`, `/var/tmp`, `/dev/shm`;
- неизвестный модуль ядра;
- модуль, не принадлежащий пакету;
- чужие `authorized_keys`;
- второй пользователь с UID 0;
- неизвестный пользователь в:
  - `sudo`
  - `docker`
  - `lxd`
  - `libvirt`
  - `disk`
  - `kvm`
- `/etc/ld.so.preload`;
- `LD_PRELOAD` в системных конфигах;
- неизвестный `AuthorizedKeysCommand`;
- неизвестный `TrustedUserCAKeys`;
- изменения системных бинарников по `dpkg -V` или `debsums`;
- неизвестные `.efi` файлы;
- подозрительные записи в `efibootmgr`.

### Умеренная подозрительность

- `rwxp` у браузера, Java, .NET, NodeJS;
- удалённый `exe` после обновления пакета;
- несколько сетевых namespace при наличии Docker/VPN;
- `AuthorizedKeysCommand`, используемый известной инфраструктурой;
- `TrustedUserCAKeys`, используемый корпоративной инфраструктурой.

### Низкая подозрительность

- все процессы принадлежат известным пакетам;
- файлы находятся в стандартных системных каталогах;
- `dpkg -V` не показывает изменения критичных бинарников;
- сетевые соединения объясняются сервисами;
- конфигурация SSH соответствует ожидаемой.

---

## 14. Ложные срабатывания

### `rwxp`

Может быть у:

- браузеров;
- Java;
- .NET;
- NodeJS;
- Python JIT-компонентов;
- эмуляторов;
- GPU-драйверов.

### Удалённый `exe`

Может быть после:

- обновления пакета;
- перезапуска демона;
- замены бинарника без перезапуска процесса.

### Сетевые namespace

Могут быть у:

- Docker;
- Podman;
- LXC;
- libvirt;
- VPN;
- systemd-nspawn;
- браузерных песочниц.

### Сравнение `/proc/net/tcp` и `ss`

Ложные срабатывания возможны из-за:

- быстрых изменений состояния сокетов;
- кратковременных соединений;
- IPv6;
- особенностей вывода `ss`.

### `rkhunter`, `chkrootkit`, `lynis`

Могут:

- давать ложные срабатывания;
- ругаться на проприетарные драйверы;
- не видеть сложные угрозы;
- требовать актуальных баз и корректного состояния системы.

## 16. Офлайн-проверка с Live USB

Если есть серьёзные подозрения, рекомендуется:

1. Скачать официальный образ доверенного Live Linux.
2. Проверить контрольные суммы образа.
3. Записать образ на чистый носитель.
4. Загрузиться с него.
5. Не монтировать подозрительный диск в режиме записи без необходимости.
6. Смонтировать корневой раздел подозрительной системы только для чтения:

```bash
mount -o ro,noatime /dev/sdXn /mnt
```

Для LUKS:

```bash
cryptsetup luksOpen /dev/sdXn cryptroot
mount -o ro,noatime /dev/mapper/cryptroot /mnt
```

Для btrfs может потребоваться указать подтом:

```bash
mount -o ro,subvol=@ /dev/sdXn /mnt
```

Далее можно анализировать:

```text
/mnt/etc
/mnt/var/log
/mnt/usr/bin
/mnt/usr/sbin
/mnt/boot
/mnt/boot/efi
/mnt/root/.ssh
/mnt/home/*/.ssh
```

## 17. Действия при инциденте

Если найдены серьёзные красные флаги:

1. Не вводите важные пароли, ключи и коды 2FA на подозрительной системе.
2. Сохраните отчёт:

   ```bash
   sudo ./ir_check.sh pack
   ```

3. Скопируйте архив на внешний носитель или доверенный хост.
4. Отключите машину от сети.
5. При необходимости сохраните образ диска или оперативную память, если есть соответствующие навыки.
6. Перейдите к офлайн-проверке с Live USB.
7. При подтверждении компрометации:
   - переустановите систему;
   - обновите UEFI/BIOS;
   - удалите неизвестные загрузочные записи;
   - смените пароли;
   - перевыпустите SSH-ключи;
   - отзовите токены;
   - завершите активные сессии;
   - проверьте роутер и сетевые настройки.

## 18. Диагностика типовых проблем

### `apt-get update` завершился с ошибкой

Возможные причины:

- нет сети;
- недоступны репозитории;
- неверные источники пакетов;
- проблемы с DNS;
- требуется прокси.

Проверки можно запустить без установки пакетов:

```bash
sudo ./ir_check.sh all
```

Но часть функций будет недоступна.

---

### `sshd -T` завершился с ошибкой

Возможные причины:

- отсутствует `/etc/ssh/sshd_config`;
- ошибка в конфигурации;
- отсутствуют хостовые ключи;
- пакет `openssh-server` установлен частично.

Проверьте:

```bash
sudo sshd -t
```

Если пакет установлен, но ключей нет:

```bash
sudo dpkg-reconfigure openssh-server
```

> [!NOTE]
> Выполняйте `dpkg-reconfigure` только если понимаете последствия и уверены, что это уместно на данной системе.

---

### `efibootmgr` недоступен

Возможные причины:

- система загружена в режиме BIOS;
- EFI variables не смонтированы;
- пакет `efibootmgr` не установлен.

Проверка типа firmware:

```bash
[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS
```

---

### `fwupdmgr` недоступен или завершился с ошибкой

Возможные причины:

- пакет `fwupd` не установлен;
- сервис `fwupd` не запущен;
- оборудование не поддерживает обновление через `fwupd`;
- недостаточно прав.

Проверка:

```bash
systemctl status fwupd
```

---

### `auditctl` не найден

Установите `auditd`:

```bash
sudo apt install auditd
```

После этого можно запускать:

```bash
sudo ./ir_check.sh audit-ssh
```

---

### `latest` не найден

Это значит, что ещё не было выполнено ни одной проверки или каталог `/root/ir` был удалён.

Выполните:

```bash
sudo ./ir_check.sh full
```

или:

```bash
sudo ./ir_check.sh all
```

---

### Очистка не удаляет пакеты

Возможные причины:

- отсутствует файл состояния;
- пакеты уже были установлены до запуска `00_ir_setup.sh`;
- пакеты были удалены вручную;
- используется неполный список очистки.

Проверьте:

```bash
cat /root/ir/state/setup_installed_packages.txt
```

Если файла нет, можно использовать:

```bash
sudo ./90_ir_cleanup.sh --all --known-packages --dry-run
```

Затем, если результат корректный:

```bash
sudo ./90_ir_cleanup.sh --all --known-packages
```

---

### Нет `99-summary.txt`

Скорее всего, не был запущен скрипт сводки.

Выполните:

```bash
sudo ./95_ir_summarize.sh
```

После этого файл должен появиться:

```text
/root/ir/latest/99-summary.txt
```

```bash
  16_ir_ssh_audit.sh
  20_ir_integrity.sh
  30_ir_modules.sh
  40_ir_boot.sh
  50_ir_network.sh
  55_ir_custom.sh
)
```

4. При необходимости добавьте отдельный пункт меню или команду.

## 20. Безопасность использования очистки

Рекомендуемый порядок:

1. Упаковать отчёт:

   ```bash
   sudo ./ir_check.sh pack
   ```

2. Скопировать архив в безопасное место.

   ```bash
   sudo ./ir_check.sh cleanup-all
   ```

```bash
sudo ./90_ir_cleanup.sh --all --known-packages
```

Если нужно выполнить очистку без интерактивных подтверждений:

```bash
sudo ./90_ir_cleanup.sh --all --known-packages --autoremove --force
```

> [!CAUTION]
> Режим `--force` выполняет действия без запроса подтверждения.
>
> Используйте его только в автоматизации и только если понимаете последствия.

## 21. Часто задаваемые вопросы

### Можно ли использовать набор на сервере?

Да, но с осторожностью. Некоторые проверки могут быть ресурсоёмкими, особенно:

- `15_ir_anomalies.sh`;
- `20_ir_integrity.sh`;
- `60_ir_scanners.sh`;
- `lsof +D /proc`, если включён через `IR_ENABLE_LSOF_PROC=1`.

На нагруженном сервере сначала тестируйте в нерабочее время или на копии.

---

### Можно ли использовать набор без интернета?

Да, но без установки пакетов часть функций будет недоступна.

Если пакеты уже установлены:

```bash
sudo ./ir_check.sh all
```

Если нет:

```bash
sudo ./ir_check.sh all
```

но некоторые проверки сообщат, что нужные инструменты отсутствуют.

---

### Проверяется ли система на вирусы?

Нет, это не антивирус.

Набор собирает артефакты и ищет подозрительные шаблоны. Для проверки можно дополнительно использовать:

- `rkhunter`;
- `chkrootkit`;
- `lynis`;
- антивирусные сканеры по желанию;
- офлайн-анализ;
- анализ памяти;
- сетевой анализ.

---

### Можно ли отправлять архив с логами?

Да, но сначала проверьте, нет ли в логах конфиденциальных данных.

В логах могут быть:

- имена пользователей;
- имена хостов;
- пути к файлам;
- сетевые адреса;
- отпечатки ключей;
- названия сервисов.

Приватные ключи и пароли скрипты не собирают намеренно, но перед отправкой архив лучше проверить.

Для первичной отправки лучше использовать:

```text
99-summary.txt
```

а не весь архив целиком.

---

### Почему `rkhunter` или `chkrootkit` что-то нашли?

Это может быть:

- ложное срабатывание;
- легитимное изменение;
- проприетарный драйвер;
- обновление пакета;
- реальный индикатор компрометации.

Проверяйте находку в совокупности с другими логами.

---

### Почему `rwxp` нашёлся у браузера или Java?

JIT-компиляторы часто создают исполняемые регионы памяти. Сам по себе `rwxp` не является доказательством взлома.

Смотрите:

- процесс;
- путь к бинарнику;
- владельца;
- сетевую активность;
- наличие других красных флагов.

---

### Почему `deleted exe` появился у системного процесса?

Часто это происходит после обновления пакета: файл на диске заменён, но старый процесс ещё использует удалённый файл.

Если процесс системный и недавно было обновление, это может быть нормой.

Если процесс неизвестный, сетевой или запущен из подозрительного каталога — это повод разбираться.
